1 The Vagrantfile, as it now stands

Vagrant.configure("2") do |config|
  config.vm.box = "debian/trixie64"

  config.vm.define "smbarkiS" do |server|
    server.vm.hostname = "smbarkiS"
    server.vm.network :private_network, ip: "192.168.56.110"
    server.vm.provider :libvirt do |lv|
      lv.default_prefix = ""      # domain is named smbarkiS, not p1_smbarkiS
      lv.memory = 1024            # subject p6: 512 MB or 1024 — the server gets 1024
      lv.cpus   = 1               # subject p6: 1 CPU
    end
  end

  config.vm.define "smbarkiSW" do |worker|
    worker.vm.hostname = "smbarkiSW"
    worker.vm.network :private_network, ip: "192.168.56.111"
    worker.vm.provider :libvirt do |lv|
      lv.default_prefix = ""
      lv.memory = 512             # agent only — the bare minimum the subject asks for
      lv.cpus   = 1
    end
  end
end

Three things you need to be able to say about its shape:

It mirrors the subject's own example

📕
Subject p7

The subject prints a skeleton Vagrantfile: config.vm.box once at the top, then one define block per machine. Ours is that skeleton, filled in. When an evaluator asks "why is it structured like this?" — "it's the structure your own subject shows on page 7."

config. vs server. is scoping — and mixing them up is a real bug

Anything on config. applies to every machine; anything on the block variable applies to that machine only. Example of the mistake, taken from the subject's own skeleton — p7 writes, inside the wilS block: 

config.vm.provision :shell, :inline => SHELL   # ← config., inside a define block!
⛔
That provision runs on BOTH machines

— even though it's written inside wilS's block, because it hangs the setting on config.. If we did that with the server's K3s install line, the worker would try to install a K3s server too. Rule: inside a define block, never type config. — only the block's own variable.

Why the worker gets 512 MB and the server 1024

📕
Subject p6

"It is STRONGLY advised to allow only the bare minimum in terms of resources: 1 CPU and 512 MB of RAM (or 1024)." — the parenthesis is the permission.

The server runs the whole control plane — API server, datastore, scheduler, plus Traefik in p2 — and OOM-loops at 512. The worker runs only the K3s agent. So: minimum where it fits, the allowed 1024 where the minimum doesn't.

✓
Observed values — don't let them spook you at the defense

Server MemTotal: 990576 kB, worker MemTotal: 475244 kB. You never see the round number because the kernel keeps a slice for itself. Those values are correct.

2 The commands you'll actually type

All from inside p1/ — Vagrant finds the Vagrantfile in the current directory. With two machines, most commands now want a machine name:

CommandWhat it does
vagrant statusBoth machines and their states — your first move, always
vagrant upBrings up everything not running — it skipped smbarkiS and built only smbarkiSW in slice 1.3
vagrant up smbarkiSWJust that machine
vagrant ssh smbarkiSLog into the server (name required now — plain vagrant ssh errors with two machines)
vagrant ssh smbarkiSW -c "hostname"Run one command, print, exit — how every proof in this series is taken
vagrant destroy -fDelete both VMs, no confirmation
vagrant destroy -f smbarkiSWDelete just the worker (handy when only the agent side broke)
vagrant reload smbarkiSReboot + re-read the Vagrantfile (config changes like memory need destroy/up under libvirt)
vagrant provision smbarkiSRe-run provisioning scripts without rebooting — the fast loop once K3s scripts exist

And the hypervisor's view, from iot-host: virsh list --all (both domains), virsh net-list --all (the networks).

3 The network, as it actually exists now

p10 / virbr2
192.168.56.0/24
iot-host .1 (gateway) smbarkiS eth1 .110 static smbarkiSW eth1 .111 static
vagrant-libvirt
192.168.121.0/24
iot-host .1 smbarkiS eth0 .233 DHCP smbarkiSW eth0 .234 DHCP

Facts observed — each one a likely evaluator question:

  • p10 was reused, not duplicated. The worker's private_network line names the same subnet, so vagrant-libvirt attached it to the same virtual switch. One network, three legs: .1, .110, .111.
  • iot-host pings both VMs (~0.7 ms) — because it holds .1 on that switch. This is mechanically how p2's curl http://192.168.56.110 from "the host" will work.
  • Worker reaches server over .56: ping 192.168.56.110 from smbarkiSW → 2/2, 0% loss. The K3s join path exists before K3s does. When the agent later joins the server at https://192.168.56.110:6443, the packets take exactly the route we just proved.
⚠
The eth0 lesson, with real numbers

The server's eth0 was 192.168.121.46 on the 1.1 build and 192.168.121.233 after the 1.2 rebuild — same Vagrantfile, different address, because it's a DHCP lease that Vagrant owns. eth1 stayed .110 because we declared it. Anything that depends on eth0's address is silently broken by the next rebuild. That, in one example, is why slice 1.4 will pass --node-ip 192.168.56.110 to K3s: left alone, K3s picks the default-route interface — eth0.

4 One trade-off you must be able to defend: default_prefix = ""

Without it, the libvirt domain is named p1_smbarkiS. With it, virsh list shows plain smbarkiS — matching the subject's example, which names the machine at the provider level (v.customize [..., "--name", "wilS"], p7).

⚠
The cost — say it before the evaluator finds it

p2 will also define a domain named smbarkiS, so p1's and p2's VMs can never run at the same time — the second vagrant up would fail with a libvirt "domain already exists" error. Our working rule already requires destroying a part before testing another, so the collision can't happen in practice. Defense sentence: "p1 and p2 are mutually exclusive by design; the clean-run rule destroys one before booting the other."

5 Slice 1.4 as built — K3s server, and what the proofs showed

The server block now runs scripts/server.sh (a scripts/ folder is mandated by p17's yellow box; provision "shell", path: is the subject's own p7 pattern). The script, in plain words: find which interface carries .110 (never hardcoded — p8's info box), install K3s pinned to v1.36.3+k3s1 in server mode with the pre-seeded token and --node-ip, make kubectl work without sudo, and refuse to finish until the node is actually Ready. Install took 1m02; the node was Ready one second after registering.

What the proof commands showed — four moments you'll want at the defense:

  • kubectl get nodes with no sudo, no flags, no path — because the installer symlinked /usr/local/bin/kubectl → k3s (that alone satisfies p6's yellow box: ls -l /usr/local/bin/kubectl is the proof), and /etc/profile.d/k3s.sh points it at the kubeconfig.
  • NAME smbarkis — lowercase. The hostname is still smbarkiS (hostname proves it); Kubernetes canonicalises node names because they are DNS labels, and DNS labels forbid uppercase. Rehearsed sentence: "the hostname is smbarkiS as required; the node object is lowercase because node names are RFC-1123 DNS labels."
  • INTERNAL-IP 192.168.56.110 — --node-ip doing exactly what the eth0 lesson predicted it must. Without it, this column would read 192.168.121.x and change on every rebuild — the subject's p8 "not complete" screenshot is precisely that failure.
  • ROLES control-plane — no master. The legacy master label was removed upstream; K3s v1.36 no longer applies it. Older tutorials and screenshots show control-plane,master — ours showing one label is correct, not a regression.
✓
One flag we deliberately did NOT pass — with receipts: --tls-san

Tutorials add it "so the API cert covers the IP" — but K3s derives the cert's names from --node-ip automatically. Proved from iot-host:

echo | openssl s_client -connect 192.168.56.110:6443 | openssl x509 -noout -ext subjectAltName
→ … IP Address:192.168.56.110 … — present, no --tls-san anywhere.

An unexplainable flag is a question waiting to be asked; a removed flag with a proof is an answer waiting to be given.

Next: slice 1.5 — the agent joins

scripts/worker.sh on smbarkiSW: same pre-seeded token, K3S_URL=https://192.168.56.110:6443, agent mode (subject p6: "In the second one (ServerWorker), in agent mode"), plus one guard — wait until the server's API answers before installing, so a fast worker can't race a slow server. The join uses exactly the network path we proved with ping in slice 1.3. Proof: kubectl get nodes -o wide on the server shows two Ready nodes, .110 / .111, roles control-plane / <none>.

6 The crisis — how p1 nearly died, and what fixed it

This actually happened, between slices 1.4 and 1.5. Learn it as a story; it contains the best defense answers p1 will ever give you.

StageWhat we saw
SymptomThe worker's agent looped forever on "Waiting to retrieve agent configuration… context deadline exceeded". Timeout — which smells like a network problem.
False leadIt wasn't the network: slice 1.3 had proved the path with ping, and the join guard had already seen the server answer once.
The tellA plain kubectl get nodes on the server also hung. When the joiner and an unrelated command both stall, the common factor is the server.
Evidenceload average: 23 on one vCPU. 6 MB available out of 967. The server was thrashing — too starved to answer anyone, including the agent knocking at the door.

The cause. K3s isn't just Kubernetes; it bundles extras — Traefik, ServiceLB, metrics-server, a storage provisioner — all pods, all RAM, all API-server load. On v1.36 the full bundle plus a node join no longer fits in 1024 MB. It ran fine for 40 minutes (fresh caches, no load) and collapsed exactly when the join added pressure. "It worked when I tested it" is not the same as "it survives load."

✓
The fix — more subject-compliant, not less

p1 needs none of those extras: the subject asks for a bare two-node cluster. So server.sh passes --disable traefik --disable servicelb --disable metrics-server --disable local-storage, and RAM stays at the subject's blessed 1024/512. Measured: 6 MB → 313 MB available; load 23 → 1.0; the only pod left is coredns.

Defense sentence: "K3s bundles optional add-ons; part 1 uses none, so they are disabled — that is the bare minimum the subject advises, applied to software as well as hardware." p2 re-enables exactly what it uses (Traefik and ServiceLB) and nothing more.

Two bonus finds from the same crisis:

  • My kubectl wait guard had a bug: kubectl get node exits 0 even when it prints "No resources found", so the wait could fire before the node object existed. The guard now counts node objects. Lesson: an exit code is not a fact about the world.
  • vagrant-libvirt provisions machines in parallel, not in definition order. The worker was installing while the server was still mid-provision. The worker's until curl …/cacerts loop is therefore load-bearing, not decorative — without it, the cold boot is a race you sometimes lose, and "sometimes" includes defense day.

8 Test yourself

1A provision line written inside the smbarkiS block starts with config. — what happens?›

It applies to every machine, not just smbarkiS — the worker would run the server's provisioning too. Inside a define block, only use the block's own variable. → §1

2The evaluator runs free -m on the worker and sees ~464 MB, not 512. Problem?›

No. The kernel reserves memory for itself; MemTotal is what's left. Observed: 475244 kB on the worker, 990576 kB on the server. Correct values. → §1

3Plain vagrant ssh now errors. Why, and what's the fix?›

With two defined machines Vagrant needs to know which one: vagrant ssh smbarkiS or vagrant ssh smbarkiSW. → §2

4Who answers at 192.168.56.1, and why does that address exist?›

iot-host itself — vagrant-libvirt gave it the gateway leg of the virtual switch (virbr2) it built from our private_network lines. It's also why the host can ping/curl the VMs at all. → §3

5Prove — with a command that works today — that the worker will reach the K3s API in slice 1.5.›

vagrant ssh smbarkiSW -c "ping -c 2 192.168.56.110" → 2/2, 0% loss. The agent will dial https://192.168.56.110:6443 over that exact route. → §3

6Why can't p1 and p2 run at the same time, and why is that acceptable?›

Both name a domain smbarkiS (because default_prefix = ""). Acceptable because the clean-run rule destroys one part before booting another — and it matches the subject's provider-level naming example. → §4

7The server's eth0 changed between two builds. Recite the numbers and the conclusion.›

192.168.121.46 → 192.168.121.233. DHCP plumbing changes; declared addresses don't. Never let the cluster depend on eth0 — hence --node-ip. → §3, §5

8"Why does kubectl get pods -A show almost nothing — where is Traefik?"›

Disabled on purpose, with the subject as justification: p6 — "allow only the bare minimum". p1 needs no ingress, no LB, no metrics, no storage; K3s's optional add-ons are switched off and p2 re-enables exactly what it uses. Bonus: that's also what makes the cluster fit in 1024 MB on v1.36. → §6

9The agent loops on "context deadline exceeded" fetching CA certs. Walk the diagnosis.›

Don't chase the network first — check whether the server answers anything at all (kubectl on the server, uptime, free). The numbers that told the truth: load 23 on 1 vCPU, 6 MB available. A timeout from a thrashing server looks identical to a broken network from the client's side. → §6

10Why is the worker's wait-for-server loop not optional on this provider?›

Because vagrant-libvirt provisions machines in parallel — observed: the agent was installing while the server was mid-provision. Without until curl …/cacerts, the cold boot is a race. → §6
