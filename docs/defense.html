The script for the day

Defense runbook — how to present p1 and p2

The other pages teach concepts; this one is the script: the order, the commands, what to say while things boot, the questions that are coming, and what to do when something breaks. Evaluation happens on OUR machine (p17), driven by you.

p1 builds in ~3 min · p2 in ~10 min· Something is always building while you are always explaining

0 Pre-flight — before the evaluator sits down

⛔
EVERYTHING in this runbook runs INSIDE iot-host — never on the laptop

The laptop has no Vagrant, no virsh, no clusters, by design; it only hosts the outer VM. The first command below (ssh iot-host) is the one that changes machines. Check your prompt before typing anything else:
sabdark@sabdark-NKx0Kx = laptop (wrong place) · sabdark@iot-host = inside (right place).
The repo path differs too: inside it is ~/Inception-of-things, not ~/Desktop/1337/….

Run these yourself, alone, that morning:

ssh iot-host                                  # the outer VM is up (it autostarts)
cd Inception-of-things && git pull            # repo inside matches main
cd p1 && vagrant destroy -f; cd ../p2 && vagrant destroy -f
virsh list --all                              # MUST be empty — no stale domains
vagrant box list                              # debian/trixie64 cached (no download mid-demo)
free -h                                       # iot-host has its ~5 GB free

On the laptop: close heavy apps (the desktop eats RAM the VMs need), and have docs/ open in a browser tab — organized docs never hurt.

✓
Arrive with everything DOWN

The clean build from zero is the demo. A pre-booted cluster invites "how do I know you didn't hand-fix this?" — a cold vagrant up answers it before it's asked.

1 The opening — 60 seconds, before any command

"The whole project runs inside a virtual machine, as page 4 requires — this laptop hosts one big VM, iot-host, and everything you'll see runs inside it. Vagrant works there with the libvirt provider — page 4's blue box allows any provider. Part 1 is a two-node K3s cluster on two Vagrant VMs; Part 2 is one VM serving three apps behind one Ingress; Part 3 is K3d and Argo CD, no Vagrant. I'll build each part from zero in front of you."

Why this order of ideas: it plants the three subject citations for the outer VM (p4 ×2, p12) before the evaluator can ask "why nested VMs?", and it sets the expectation that builds happen live.

2 Part 1 — the script

2.1 Launch first, talk second

ssh iot-host
cd Inception-of-things/p1
vagrant destroy -f && vagrant up        # ~3 min — the talking window opens now

2.2 While it builds — walk the Vagrantfile (open in a second terminal)

  • Shape: "one config.vm.box at the top, one define block per machine — the structure page 7 of the subject itself shows."
  • Names: "machine name, hostname and libvirt domain are all smbarkiS — login smbarki + S, as page 6 demands. Same with SW for the worker."
  • IPs: "static .110/.111 on a private network — the dedicated IPs from page 6. NIC 1 belongs to Vagrant on any provider — that's how vagrant ssh works — so the dedicated IP lives on the second interface, which is why page 8's info box points at enp0s8/enp0s9, the second and third adapters."
  • Resources: "1 CPU each; worker at the 512 minimum, server at the allowed 1024 — the parenthesis in '512 MB (or 1024)' is the permission. The server runs the whole control plane; 512 would OOM."
  • The token: "pre-seeded: I tell both machines which token to use, instead of the worker fishing the generated one out of the server's filesystem. Copying it through /vagrant would drop a live credential into the git repo — it's a live NFS mount of the project — and a stale copy survives destroy and breaks the next join. I inverted the dependency."
  • The scripts: "provisioning lives in scripts/, page 17's yellow box. server.sh: detect the interface carrying .110 at runtime — page 8 says never hardcode names — then K3s pinned, server mode, --node-ip. worker.sh: same token, agent mode, and it waits for the server's API, because this provider provisions machines in parallel."
  • If asked about --disable: "K3s bundles Traefik, a load balancer, metrics-server and a storage provisioner. Part 1 needs none — the bare minimum the subject advises, applied to software. Part 2 re-enables exactly what it uses."

2.3 The proofs

vagrant ssh smbarkiS -c "kubectl get nodes -o wide"

Narrate the columns: two Ready · smbarkis/smbarkisw — "node names are RFC-1123 DNS labels, so Kubernetes lowercases them; the hostname is still capital-S, watch:" — 

vagrant ssh smbarkiS -c "hostname"        # smbarkiS, capital S, on demand

· INTERNAL-IPs .110/.111 — "that's --node-ip; without it they'd register with Vagrant's DHCP plumbing" · ROLES control-plane and <none> — "the legacy master label was removed upstream." 

vagrant ssh smbarkiS -c "ls -l /usr/local/bin/kubectl"   # -> k3s: p6 yellow box, by the installer
vagrant ssh smbarkiSW -c "systemctl is-active k3s-agent" # agent mode, alive
ping -c1 192.168.56.110 && ping -c1 192.168.56.111       # reachable from the host

2.4 Close p1, open p2 — say the sentence before they find the trap

vagrant destroy -f          # in p1/
"p1 and p2 both name their domain smbarkiS — matching the subject's provider-level naming — so they're mutually exclusive by design; I destroy one before booting the other."

3 Part 2 — the script

3.1 Launch, then use the long build

cd ../p2 && vagrant up      # ~10 min cold — say why up front:
"This takes about ten minutes cold: the K3s binary and the container images are pulled fresh — nothing is pre-staged except the Vagrant box. The build is fully self-checking: it will refuse to finish unless all four routing cases already work."

3.2 While it builds — walk the three files

confs/apps.yaml — "three Deployments and three ClusterIP Services in the default namespace — page 11's kubectl get all has no -n, so that's where your command will look. One pinned image for all three, traefik/whoami: a tiny server that answers with its own pod name — that's how I prove things instead of claiming them. replicas: 3 on app-two is the blue box on page 9, one line."

confs/ingress.yaml — the centerpiece (p11's red box: shown and explained live):

  • "Standard networking.k8s.io/v1, class traefik — the controller K3s ships; no second controller installed."
  • "Two objects, and the split is Traefik's requirement, which I verified live: Traefik v3.7 ignores defaultBackend when the same Ingress also carries rules — I watched the API object show the default while the route 404'd. Rules in apps, the default alone in apps-default."
  • "Why defaultBackend instead of a host-less rule? A host-less rule only loses by an accident of Traefik's rule-length sorting. defaultBackend compiles to a priority that cannot be outranked — it means 'when nothing else matches', the subject's own word: otherwise… by default."

scripts/server.sh — "same skeleton as p1's, three deliberate differences: no token (no worker), Traefik and ServiceLB on (they are the routing), and success is defined as the router serving — the script curls all four cases itself before it exits."

3.3 The proofs — all from the iot-host shell

"The host in the subject's sense is this VM; the 192.168.56 network exists only inside it."

curl -H "Host: app1.com" http://192.168.56.110        # Name: app1
curl -H "Host: app2.com" http://192.168.56.110        # Name: app2
curl http://192.168.56.110                            # Name: app3  ← "otherwise"
curl -H "Host: whatever.xyz" http://192.168.56.110    # Name: app3  ← still "otherwise"

# the replica proof — 9 requests, count the pod names:
for i in $(seq 9); do curl -s -H "Host: app2.com" http://192.168.56.110 | grep "^Hostname:"; done | sort | uniq -c

Then the red-box moment — show and narrate:

vagrant ssh smbarkiS -c "kubectl get all"              # the exact p11 screenshot shape
vagrant ssh smbarkiS -c "kubectl describe ingress"     # both objects, one screen
"Two rules — app1.com and app2.com, each to its Service; app2's Service fronts three endpoints, which you just saw rotate. And the separate default object sends everything else to app-three."

3b Self-test p2 — the drill you run alone

Everything the evaluator will do, done by yourself first. All inside iot-host.

Step 0 — position

ssh iot-host
cd Inception-of-things/p2

Step 1 — alive?

vagrant status → smbarkiS running. If not created: vagrant up (6–10 min, self-checking) is the only repair p2 ever needs.

Step 2 — look inside

vagrant ssh smbarkiS -c "kubectl get all"

Check three things: 5 pods Running (1 + 3 + 1) · app-two 3/3 · three ClusterIP services on port 80. You typed no -n — this is p11's screenshot, live, in the default namespace.

Step 3 — the four routing cases (on iot-host directly)

curl -H "Host: app1.com" http://192.168.56.110          # → Name: app1
curl -H "Host: app2.com" http://192.168.56.110          # → Name: app2
curl http://192.168.56.110                              # → Name: app3
curl -H "Host: banana.whatever" http://192.168.56.110   # → Name: app3

Named hosts reach their apps; anything else falls to app3. Try your own garbage hostnames — all must answer app3.

Step 4 — replicas share the work

for i in $(seq 9); do curl -s -H "Host: app2.com" http://192.168.56.110 | grep "^Hostname:"; done | sort | uniq -c

→ three different pod names, 3 each. One name ×9 = broken.

Step 5 — show the Ingress (the p11 red-box screen)

vagrant ssh smbarkiS -c "kubectl get ingress"
vagrant ssh smbarkiS -c "kubectl describe ingress"

Two objects at .110; in the describe: both rules (app-two with three endpoint IPs) and Default backend: app-three:80. Practice narrating it once.

Step 6 — the ultimate test

vagrant destroy -f && time vagrant up

Ends with four routing OK lines, zero manual steps. Then repeat steps 2–5 on the fresh machine.

4 The question bank — answers you already own

QuestionThe answer (one breath)
Why is everything inside a VM?p4: "the whole project has to be done in a virtual machine" — plus p4's blue box says "host virtual machine", and p12 says install K3d "on your virtual machine" with no Vagrant in sight. Three citations, one outer VM.
Why libvirt, not VirtualBox?The subject allows any provider (p4 blue box). Technically: VirtualBox can't nest reliably inside KVM, and its kernel modules lag new kernels.
K3s vs K3d?K3s is a lightweight Kubernetes distribution — one binary on the machine. K3d runs K3s inside Docker containers — each "node" is a container. p1/p2 use K3s in VMs; p3 uses K3d, hence no Vagrant.
How does the worker get the token?It doesn't "get" it — both machines are given the same pre-seeded token by the Vagrantfile. Nothing copied, nothing in the repo, nothing stale after destroy.
Why lowercase in get nodes?Node names are RFC-1123 DNS labels; uppercase is forbidden. The hostname itself is smbarkiS — hostname proves it.
Why no master in ROLES?Removed upstream; modern K3s applies only control-plane. Same node, the alias is gone.
"Dedicated IP on the primary interface"?Vagrant owns NIC 1 on every provider — the subject's own p8 box points at enp0s8/enp0s9, the second and third adapters. Primary = the interface the cluster uses; --node-ip makes it explicit.
Where's Traefik in p1?Disabled deliberately: p1 needs no ingress, LB, metrics or storage — "bare minimum" applied to software. p2 re-enables what it uses.
Why two Ingress objects?Traefik v3.7 ignores defaultBackend when rules coexist in the object — verified live. Rules in one, default in the other; only one may declare a default.
Prove the replicas load-balance.The 9-curl loop: three pod names, three hits each.
What listens on port 80?K3s's ServiceLB, holding the hostPort for Traefik's LoadBalancer Service. Nothing else may claim 80/443.
Is 1024 MB enough?The subject's "(or 1024)". p2 idles at ~86 MB free with the full stack — thin but stable: nothing further ever loads this machine.
Why 990/475 MB, not 1024/512?The kernel reserves a slice for itself; MemTotal is what remains. Correct values.

5 If something breaks — the emergency card

⚠
Rule one: narrate, don't panic. Rule two: rebuild, never hand-fix and pretend.

You have already diagnosed worse than anything likely to happen. Three to ten minutes of rebuild is affordable; a caught lie is not.

SymptomMove
vagrant up: domain already exists virsh list --all; vagrant destroy -f in the other part's folder (or virsh destroy + undefine)
Vagrant lock held by another process pgrep -af ruby → kill the stale PID → retry
A curl times out Check the server first, not the network: vagrant ssh smbarkiS -c "uptime; free -m" — you know what thrash looks like
Agent loops "waiting to retrieve agent configuration" Same move: server health first. That exact symptom was the p1 crisis.
Traefik 404 on a host that should route kubectl get ingress; give Traefik ~5 s; then describe ingress and read it aloud — the diagnosis is a demonstration of competence
Unrecoverable mid-demo Say so, vagrant destroy -f && vagrant up, keep talking through the files while it rebuilds — build time is presentation time by design

6 What NOT to do

  • Don't type commands you haven't rehearsed — everything needed is in this runbook and iot-verify.
  • Don't kubectl edit/set image/hand-patch live. Git is the truth; rebuilds are cheap.
  • Don't guess at a question. "Let me show you" + a command beats an improvised theory — every §4 answer has a command behind it.
  • Don't start the bonus conversation. It's evaluated only if the mandatory part is flawless (p16 red box) — let the mandatory part finish flawlessly first.

7 Rehearsal checklist — at least once before the real thing

  • Full run of §2 + §3 solo, out loud, with a timer — target under 25 min including talk
  • /iot-defense p1 and /iot-defense p2 — the mock evaluator drill
  • Every §4 answer spoken from memory, not read
  • Once with sabotage: someone pre-creates a stale domain, then you start — §5 should feel boring
