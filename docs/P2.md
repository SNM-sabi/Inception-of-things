## 1. What p2 actually is, in one picture

Subject p9: *"You will set up 3 web applications... You will have to be able to access
them depending on the HOST used when making a request to the IP address 192.168.56.110."*

```
                      ┌──────────────────────── the VM (smbarkiS, .110) ───────┐
curl -H "Host: app1.com" ──┐                    │                              │
curl -H "Host: app2.com" ──┼──► port 80 ──► Traefik ──► app1  (1 pod)          │
curl (anything else)     ──┘        (the door)  │   └──► app2  (3 pods!)       │
                                                │   └──► app3  (1 pod, DEFAULT)│
                                                └──────────────────────────────┘
```

One machine, one IP, one port — and **the request itself says which app it wants**, via
the `Host:` header. That's the whole exercise: teaching one door to route to three rooms.

### What is this "Host header"?

When a browser fetches `http://app1.com/`, it does two separate things: (1) looks up
`app1.com` in DNS to get an IP, and (2) connects to that IP and sends
`Host: app1.com` inside the HTTP request. Step 2 is how one server can host many sites —
it reads the header and picks. `curl -H "Host: app1.com" http://192.168.56.110` skips DNS
entirely (we give the IP) but still sends the header — which is why **no `/etc/hosts`
editing is needed**: the test never resolves `app1.com` at all.

## 2. Concept: Deployment — "keep N copies of this running"

You don't run containers directly in Kubernetes. You write a **Deployment**: a promise
you ask the cluster to keep — *"there shall be N pods (running containers) built from
this image, forever."* If a pod dies, the Deployment replaces it. If you set `replicas: 3`,
you get three identical pods — which is exactly the subject's blue box: *"application
number 2 has 3 replicas. Adapt your configuration to create the replicas."* One line of
YAML, that's the adaptation.

We use one image for all three apps: **`traefik/whoami:v1.12.0`** — a 5 MB web server
whose whole job is answering "who am I": its first line of response is the **pod's own
name**, and an env var `WHOAMI_NAME` lets us stamp each app's identity into the reply.
Chosen precisely because it makes every proof observable:

- three visibly different responses for the three apps (the subject demands you can tell them apart);
- and the killer proof for replicas: 9 curls to app2, `head -1` of each → **three different
  pod names appearing** = load-balancing demonstrated, not claimed.

## 3. Concept: Service — a stable address in front of moving pods

Pods die and are replaced, and every new pod gets a new IP. A **Service** is the fix: a
permanent virtual IP (a "ClusterIP") with a name, which forwards to whatever pods
currently match its selector — and if several match (app2's three), it **load-balances**
between them. That's the mechanism the replica proof exercises.

p11's screenshot pins down our shape: services named after the apps, **ClusterIP**, port
**80**, in the **`default` namespace** (the screenshot's `kubectl get all` has no `-n`
flag — so that's where the evaluator will look, so that's where the apps live).

## 4. Concept: Ingress — the routing table for the one door

Services give each app a *cluster-internal* address. The **Ingress** is the object that
maps *outside* traffic onto them: "Host `app1.com` → service app1; Host `app2.com` →
service app2; anything else → app3." Someone has to *implement* that table — an **ingress
controller**. Ours is **Traefik, already inside K3s** (that's why p2's `server.sh` keeps
it enabled). We write one standard `networking.k8s.io/v1` Ingress object; Traefik watches
and obeys.

Two decisions here are the difference between "works" and "works for the right reason":

**app3 is `spec.defaultBackend`, not a host-less rule.** Both *look* right in a demo. But
a rule with no host becomes an ordinary lowest-priority route by *accident* of Traefik's
rule-sorting (longer rule strings win), while `defaultBackend` compiles to a priority that
**cannot** be outranked — it is the mechanism whose *meaning* is "when nothing else
matches". The subject's word is *"Otherwise, app3 will be selected by default"* — we use
the construct that says exactly that.

**Two Ingress objects — and the split is Traefik's requirement, observed live.** We
planned one object holding both the rules and the default. Reality: **Traefik v3.7
ignores `defaultBackend` when the same Ingress also carries rules** — the API object
showed the default, the router never materialised, bare-IP curl stayed 404. Moving the
default into its own rule-less Ingress fixed it instantly. The real singleton constraint
is on the *default declaration*: only one Ingress may declare one (a second is silently
dropped). p11's red box walkthrough is unharmed — `kubectl describe ingress` with no name
shows both objects on one screen.

## 5. How a curl actually reaches a pod — the full chain

Worth reciting once, because "how does the request get in?" is a guaranteed question:

```
curl on iot-host (.56.1)
 → VM eth1 192.168.56.110, port 80        ← who's listening? ServiceLB
 → svclb pod (hostPort 80)                ← K3s's built-in LoadBalancer
 → Traefik pod                            ← reads Host header, consults Ingress
 → Service of the matching app            ← stable address, load-balances
 → one of the app's pods                  ← whoami answers, names itself
```

Nothing was installed to make port 80 work: Traefik's Service is type `LoadBalancer`, and
K3s ships **ServiceLB**, which grabs hostPort 80/443 on the node for it. (Corollary worth
knowing: nothing else on the VM may claim port 80.) This is also why the p1 crisis fix
disabled ServiceLB *there* — p1 had nothing to serve — and re-enables it *here*, where it
is the doorway.

## 6. p2's server.sh vs p1's — every difference is a sentence

| Difference | Why |
|---|---|
| **No `K3S_TOKEN`** | No worker exists. A join token would serve nothing — and every unexplainable line is a question waiting to be asked. |
| **Traefik + ServiceLB enabled** | p2 is about routing; these two *are* the routing. |
| **metrics-server + local-storage still disabled** | p2 uses neither; p1 taught us the full bundle doesn't fit 1024 MB on v1.36. |
| **Success = Traefik answers on :80** | "Node Ready" isn't the finish line here; the router serving is. The provisioner waits for it. |

And a prediction the build will test: **before any app exists, `curl http://192.168.56.110`
returns Traefik's `404 page not found`.** A 404 sounds like failure — here it's the router
saying "I'm alive; I just have nowhere to send you." Connection refused/timeout would mean
2.1 failed; 404 means it passed.
