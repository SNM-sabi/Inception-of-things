## 1. The Vagrantfile, as it now stands

```ruby
Vagrant.configure("2") do |config|
  config.vm.box = "debian/trixie64"

  config.vm.define "smbarkiS" do |server|
    server.vm.hostname = "smbarkiS"
    server.vm.network :private_network, ip: "192.168.56.110"
    server.vm.provider :libvirt do |lv|
      lv.default_prefix = ""      # domain is named smbarkiS, not p1_smbarkiS
      lv.memory = 1024            # subject p6: 512 MB or 1024 — the server gets 1024
      lv.cpus   = 1               # subject p6: 1 CPU
    end
  end

  config.vm.define "smbarkiSW" do |worker|
    worker.vm.hostname = "smbarkiSW"
    worker.vm.network :private_network, ip: "192.168.56.111"
    worker.vm.provider :libvirt do |lv|
      lv.default_prefix = ""
      lv.memory = 512             # agent only — the bare minimum the subject asks for
      lv.cpus   = 1
    end
  end
end
```

Three things you need to be able to say about its **shape**:

**It mirrors the subject's own example.** Page 7 of the subject prints a skeleton
Vagrantfile: `config.vm.box` once at the top, then one `define` block per machine.
Ours is that skeleton, filled in. When an evaluator asks "why is it structured like
this?", the answer is one sentence: *"it's the structure your own subject shows on page 7."*

**`config.` vs `server.` is scoping, and mixing them up is a real bug.** Anything on
`config.` applies to *every* machine; anything on the block variable applies to *that
machine only*. Example of the mistake, using the subject's own skeleton — p7 writes,
inside the `wilS` block:

```ruby
config.vm.provision :shell, :inline => SHELL   # ← config., inside a define block!
```

That provision would run on **both** machines even though it's written inside `wilS`'s
block — because it hangs the setting on `config.`. If we did that with, say, the server's
K3s install line, the worker would try to install a K3s *server* too. Rule: inside a
`define` block, **never** type `config.` — only the block's own variable.

**Why the worker gets 512 MB and the server 1024.** Subject p6: *"It is STRONGLY advised
to allow only the bare minimum in terms of resources: 1 CPU and 512 MB of RAM (or 1024)."*
The parenthesis is the permission. The server runs the whole control plane — API server,
datastore, scheduler, plus Traefik in p2 — and OOM-loops at 512. The worker runs only the
K3s agent. So: minimum where it fits, the allowed 1024 where the minimum doesn't. Observed
values (kernel keeps a slice for itself, so you never see the round number): server
`MemTotal: 990576 kB`, worker `MemTotal: 475244 kB`. **Those are correct** — don't let
the missing ~35 MB spook you at the defense.

## 2. The commands you'll actually type (multi-machine cheat sheet)

All from inside `p1/` — Vagrant finds the Vagrantfile in the current directory.
With two machines, most commands now want a machine name:

| Command | What it does |
|---|---|
| `vagrant status` | Both machines and their states — your first move, always |
| `vagrant up` | Brings up **everything not running** — it skipped smbarkiS and built only smbarkiSW in slice 1.3 |
| `vagrant up smbarkiSW` | Just that machine |
| `vagrant ssh smbarkiS` | Log into the server (name required now — plain `vagrant ssh` errors with two machines) |
| `vagrant ssh smbarkiSW -c "hostname"` | Run one command, print, exit — how every proof in this series is taken |
| `vagrant destroy -f` | Delete **both** VMs, no confirmation |
| `vagrant destroy -f smbarkiSW` | Delete just the worker (handy when only the agent side broke) |
| `vagrant reload smbarkiS` | Reboot + re-read the Vagrantfile (config changes like memory need destroy/up under libvirt) |
| `vagrant provision smbarkiS` | Re-run provisioning scripts without rebooting — the fast loop once K3s scripts exist |

And the hypervisor's view, from iot-host: `virsh list --all` (both domains),
`virsh net-list --all` (the networks).

## 3. The network, as it actually exists now

```
iot-host (the outer VM)
│
├─ virbr2 = 192.168.56.1        ← iot-host itself holds the gateway of "p10"
│    │
│    ├── smbarkiS   eth1 = 192.168.56.110   (static — written in the Vagrantfile)
│    └── smbarkiSW  eth1 = 192.168.56.111   (static)
│
└─ vagrant-libvirt = 192.168.121.1
     ├── smbarkiS   eth0 = 192.168.121.233  (DHCP — Vagrant's plumbing)
     └── smbarkiSW  eth0 = 192.168.121.234  (DHCP)
```

Facts observed, each one a likely evaluator question:

- **`p10` was reused, not duplicated.** The worker's `private_network` line names the
  same subnet, so vagrant-libvirt attached it to the same virtual switch. One network,
  three legs: `.1` (iot-host), `.110`, `.111`.
- **iot-host pings both VMs** (~0.7 ms) — because it holds `.1` on that switch. This is
  mechanically how p2's `curl http://192.168.56.110` from "the host" will work.
- **Worker reaches server over `.56`**: `ping 192.168.56.110` from smbarkiSW → 2/2,
  0% loss. **The K3s join path exists before K3s does.** When the agent later joins the
  server at `https://192.168.56.110:6443`, the packets take exactly the route we just proved.
- **The `eth0` lesson, with real numbers.** The server's `eth0` was `192.168.121.46` on
  the 1.1 build and `192.168.121.233` after the 1.2 rebuild — same Vagrantfile, different
  address, because it's a DHCP lease that Vagrant owns. `eth1` stayed `.110` because we
  declared it. Anything that depends on `eth0`'s address is silently broken by the next
  rebuild. That, in one example, is why slice 1.4 will pass `--node-ip 192.168.56.110`
  to K3s: left alone, K3s picks the default-route interface — `eth0`.

## 4. One trade-off you must be able to defend: `default_prefix = ""`

Without it, the libvirt domain is named `p1_smbarkiS`. With it, `virsh list` shows plain
`smbarkiS` — matching the subject's example, which names the machine at the provider level
(`v.customize [..., "--name", "wilS"]`, p7).

The cost: **p2 will also define a domain named `smbarkiS`**, so p1's and p2's VMs can
never run at the same time — the second `vagrant up` would fail with a libvirt "domain
already exists" error. Our working rule already requires destroying a part before testing
another (`vagrant destroy -f`), so the collision can't happen in practice — but say it
*before* the evaluator finds it: *"p1 and p2 are mutually exclusive by design; the
clean-run rule destroys one before booting the other."*

## 5. What's next, and why you already understand it

Slice 1.4 installs K3s on the server. The two ideas that decide whether it works, you've
now *seen* rather than read:

1. **`--node-ip 192.168.56.110`** — because of the `eth0` lesson above. K3s would
   otherwise advertise a DHCP lease that changes on every rebuild and that the subject's
   p8 screenshot explicitly shows as the *broken* configuration.
2. **The join token is pre-seeded, not copied.** The server will be *told* which token to
   use (a variable set in the Vagrantfile and passed to both machines), instead of the
   worker fishing the generated one out of the server's filesystem. Reasons you can now
   picture: `/vagrant` is a live NFS mount of the git repo — a guest-written token file
   would land next to the Vagrantfile instantly — and a stale copied token survives
   `vagrant destroy` and breaks the next join with a CA-hash mismatch.
